# 跨仓在途调拨：数量守恒与交付承诺仓

纯 Python 3.11 + SQLite 标准库实现，无第三方依赖、不接实际物流系统。
两个模块共享一个 SQLite 文件、表名空间隔离，**调拨账本是库存唯一事实源**，
交付承诺仓只读账本表、只写自己的“逐份来源占额”表，绝不复制一套库存。

## 运行

```bash
python3 demo.py          # 端到端案例（逐事件解释 + 中段/终盘/重开三重核验）
python3 edge_tests.py    # 10 项对抗性边界测试
python3 stress_test.py   # 8 个随机种子 × 40 轮混合事件流，每轮独立核验
```

演示会在当前目录生成 `demo.db`（SQLite 持久化文件），关闭重开后再核验一次。

## 模块与表

| 模块 | 表 | 职责 |
|---|---|---|
| 调拨账本 `ledger.py` | `led_event`（不可变事件日志）、`led_balance`（现货/预留物化）、`led_transfer`（调拨状态机与每笔在途）、`led_receipt`（签收凭据幂等指纹）、`led_sku_flow`（逐 SKU 累计汇总索引） | 入库、对外出库、调拨创建/发出/分次签收/损耗/未发取消 |
| 交付承诺仓 `commitment.py` | `cmt_event`、`cmt_order`、`cmt_transit_days`、`cmt_portion`（逐份来源占额）、`cmt_counter`、`cmt_meta` | 订单登记、来源分配、签收身份转换、延迟/报损失效、客户发货、全量重算 |
| 协同门面 `facade.py` | — | 共享事务编排、账本版本锚定、联动反应 |
| 独立核验 `verifier.py` | 只读 | 不 import 业务类，逐事件重放两套事件日志并交叉核对 |

固定前缀产品：事件 `LEV-######` / `CEV-######`、调拨 `TRF-####`、
签收凭据 `RCP-####`、订单 `ORD-####`、份额 `PTN-######`。

## 关键业务规则的落点

**账本侧**

- 创建调拨只预留（`reserved += qty`，现货不动）；发出时预留与现货同减、
  转为该 `transfer_id` 的在途；签收增目标仓现货，损耗只减在途。
- 守恒口径（逐 SKU）：`期初0 + 累计入库 = 现货 + 在途 + 累计损耗 + 累计对外出库`。
  预留是现货的冻结子集，**不重复计入总量**。
- 签收/损耗按 `shipped - received - lost` 限本调拨未结在途，无法挪用别的调拨；
  签收+损耗永远不超过实际发出量；发出后只能继续签收或报损，不能取消。
- 凭据 `receipt_id` 存内容哈希（transfer_id+量）：同文重投幂等返回原事件、
  库存不动；同 ID 异文直接拒绝。

**承诺侧**

- 现货可用 = `spot - 调拨预留 - 已占现货份额`；在途可用 =
  `该调拨未结在途 - 该调拨已占在途份额`，且必须有明确预计签收日。
- 订单按 优先级 DESC → 最迟日 ASC → 订单 ID ASC 逐单处理，
  **全有或全无**：净缺口不能完全覆盖则一份不占；同单来源按
  预计可交付日 → 仓 ID → 调拨 ID 定序。
- 实际签收后，在途份额经 `PORTIONS_CONVERTED` 把身份转为目标仓实物份额
  （部分签收走拆分），不释放任何在途额度给别人。
- ETA 延后导致预计交付晚于最迟日、或报损：只重判未发份额，整单回 OPEN；
  已 `SHIPPED` 的客户量不参与回滚，不可反向复活。
- 客户发货唯一入口是账本 `outbound`（原子扣真实现货）；未签收的在途
  承诺只表示计划，不计入可发实物。
- `rebuild()` 全量重算：旧未发份额标 `SUPERSEDED` 保留可追溯，
  历史 `SHIPPED` 份额与账本 `OUTBOUND` 事件原样不动。

## 两个工程取舍

### 1. 共享事务 + 版本重验，而非跨库 Saga / 分布式锁

所有写操作跑在同一个 SQLite 连接的一个显式事务里，账本写 `led_*`、
承诺仓写 `cmt_*`，同生共死，不存在“账本已扣、占额没转”的中间态。
每条承诺事件都锚定写入时的账本版本（`cmt_event.ledger_anchor_seq`），
调用方可传 `expected_ledger_version` 做乐观并发重验，版本过期即失败
（见 `demo.py` 案例 D 与 `edge_tests.test_stale_version_rejected`）。

代价：单库单写入者，吞吐受 SQLite 写锁限制；但题目规模（≤4 仓/5 SKU/
20 调拨/30 订单）下这是最直接、可线性核验的方案，不需要消息队列或
Saga 补偿。跨进程并发时应改为 WAL + 重试，接口已经预留版本号。

### 2. 逐份来源占额 + 汇总索引，而非纯实时聚合或纯快照计数

`cmt_portion` 保留每一份额的来源身份（现货仓或特定调拨）、数量、
预计日、状态机与谱系根，满足“同一份量只支持一个未结承诺、逐仓/逐调拨
可追溯”。热路径（现货占额、在途占额）用带状态列的索引实时聚合，
账本侧另维护 `led_sku_flow` 累计汇总索引让守恒查询 O(1)。

代价：拆分场景（部分签收/部分报损/部分发货）会产生新份额行，份额数
随事件增长；换来的是任何时刻都能说清“这一件货承诺给了谁、来自哪笔
调拨、现在是什么身份”，且独立核验器只需重放事件即可还原全部占额，
不依赖任何可能漂移的物化计数。

## 独立核验器在查什么

`verifier.verify()` 不信任任何物化表，从两套事件日志从零重放：

1. 逐事件检查非负、预留⊆现货、逐 SKU 守恒等式；
2. 重放的余额/调拨/汇总与库内物化表逐项比对；
3. 现货占额 ≤ 未冻结现货、在途占额 ≤ 该特定调拨未结在途；
4. 已结清调拨不得残留 HELD 在途承诺、转换量 ≤ 实际签收量；
5. 订单级活份额+已发不超过订单量，状态机与份额重放推导一致；
6. 每笔客户发货都能找到对应的账本 `OUTBOUND` 事件。

随机压力测试在**每个事件提交后**都跑一次核验，违规操作被业务层拒绝、
事务整体回滚后状态仍须满足全部不变量。
